# 基于空间可视化与智能检索的个人物品管理系统（Life-Inventory）项目企划与分工方案

## 一、项目背景

在宿舍、家庭和合租场景中，个人物品管理普遍存在三个痛点：

1. 物品位置记忆不稳定。日常“随手放置”导致需要时难以快速定位。
2. 收纳结构层级复杂。柜体、抽屉、收纳盒形成多级空间，查找路径长。
3. 信息管理方式碎片化。用户能记住“有这个东西”，却无法准确回答“在哪里、是否在库、何时过期”。

现有工具多以清单记录为主，对“空间感知”和“位置反查”支持不足。本项目拟构建一个面向日常生活场景的可视化库存系统，在不提高操作负担的前提下，实现“从物品到位置”的快速闭环。

## 二、项目目标

本项目目标不是做通用仓储系统，而是实现一个轻量、可演示、可答辩的个人物品数字化管理方案。

系统目标包括：

1. 以图片标注方式建立“存储空间-物品”的映射关系。
2. 支持物品存入、取出、迁移等完整状态流转。
3. 提供全局搜索与局部搜索，支持模糊匹配与标签检索。
4. 支持重要物品保护（收藏夹/隐私视图/访问验证）。
5. 提供过期提醒能力，覆盖药品、食品等时效物品。
6. 提供可扩展 Agent 接口，实现场景化物品推荐。
7. 形成可复制的分工与工程流程，确保 6 人团队可稳定落地。

## 三、功能设计

### 3.1 核心功能一：空间可视化定位

功能描述：

用户上传柜体、抽屉、收纳盒等空间图片后，系统支持在图片上创建标注点、矩形区域或箭头热点；每个标注可绑定一个或多个物品。用户点击标注即可查看该区域物品列表、状态和备注信息。

关键流程：

1. 创建空间节点（如卧室-书柜-第 2 层）。
2. 上传空间图片并建立坐标系。
3. 添加标注并绑定物品。
4. 点击标注反查物品详情。

功能价值：

1. 将抽象“记忆位置”转为可视化“实际位置”。
2. 查找动作由“翻找”变成“点击查看”。
3. 为后续搜索、推荐、迁移提供空间基础数据。

### 3.2 核心功能二：物品全生命周期管理

功能描述：

系统对每个物品维护结构化数据与状态机，支持新增、编辑、删除、存入、取出、迁移和历史记录。

基础字段建议：

1. 名称、分类、标签、描述。
2. 数量、单位、当前状态（在库/取出/遗失/借出）。
3. 所属位置 ID、图片、更新时间。
4. 重要级别、是否加密、过期时间。

功能价值：

1. 从“位置管理”扩展为“资产管理”。
2. 为提醒、推荐和统计提供标准化数据基础。

### 3.3 核心功能三：智能搜索与反向定位

功能描述：

系统提供统一搜索入口，支持：

1. 全局搜索（跨空间、跨分类）。
2. 局部搜索（限定某个房间或柜体）。
3. 关键词 + 标签混合查询。
4. 模糊匹配（拼写不完整、近似词）。

搜索结果需直接展示：

1. 物品当前状态。
2. 所在空间路径。
3. 对应图片标注入口（点击高亮位置）。

功能价值：

确保用户以“问答式检索”快速得到“具体在哪”。

### 3.4 扩展功能：重要物品保护、过期提醒与 Agent

1. 重要物品保护：支持收藏夹、敏感位置隐藏、二次验证查看。
2. 过期提醒：按时间窗口提示即将过期物品并支持批量处理。
3. Agent 扩展：支持“场景-物品推荐”（如感冒用药、绘画工具、出行清单）与图像辅助录入。

## 四、技术栈建议

### 4.1 总体建议

推荐采用前后端分离 + 本地可部署方案，优先保证课程实现效率与演示稳定性：

1. 前端：Vue 3 + TypeScript + Vite。
2. 后端：Node.js + Express（或 NestJS）。
3. 数据库：SQLite（首版）+ 可迁移 MySQL。
4. 对象存储：本地文件系统（首版）+ 预留云存储适配。

选择理由：

1. 上手快，团队学习成本低。
2. SQLite 便于单机演示和作业提交。
3. 结构清晰，后续可扩展移动端与 AI 服务。

### 4.2 后端技术建议

1. Web 框架：Express（快速）或 NestJS（规范）。
2. ORM：Prisma 或 TypeORM。
3. 搜索基础：SQLite FTS / SQL LIKE（首版）。
4. 认证：JWT + 会话校验。
5. 日志：Winston / Pino。

### 4.3 前端技术建议

1. UI 框架：Naive UI 或 Element Plus。
2. 状态管理：Pinia。
3. 图片标注：Konva.js（优先）或 Fabric.js。
4. 网络请求：Axios。

## 五、前后端架构设计

### 5.1 运行方式

建议命令：

`npm run dev`（开发） / `npm run start`（演示）

启动后：

1. 后端 API 服务监听本地端口。
2. 前端管理页面提供空间管理、搜索、提醒与日志视图。
3. 数据库存储在本地文件，便于课程演示与验收。

### 5.2 后端模块设计

1. Core Server

- 配置加载、路由注册、鉴权中间件、健康检查。

2. Inventory Service

- 物品 CRUD、状态流转、迁移记录。

3. Space Mapping Service

- 空间树管理、图片上传、标注坐标管理。

4. Search Service

- 关键词检索、标签检索、模糊匹配与排序。

5. Security Service

- 重要物品隐私保护、访问校验、敏感操作审计。

6. Reminder Service

- 过期检测、提醒生成、通知状态管理。

7. Agent Gateway（扩展）

- 场景化查询接口、图像识别结果接入与校正。

### 5.3 前端页面设计

1. 仪表盘

- 总物品数、在库率、临期数量、最近操作记录。

2. 空间页

- 空间树浏览、图片标注、热点点击反查。

3. 物品页

- 增删改查、状态切换、迁移记录查看。

4. 搜索页

- 全局/局部搜索、结果定位、高亮回跳。

5. 提醒页

- 过期列表、处理建议、批量标记。

6. 设置页

- 分类模板、标签词典、隐私策略、系统参数。

## 六、可行性分析

### 6.1 空间可视化部分可行性

该部分可行性高。理由如下：

1. 图片上传与坐标标注已是成熟前端能力。
2. 坐标-物品绑定属于标准数据库关系映射。
3. 首版只需支持单张图和基础热点，不依赖复杂三维建模。

### 6.2 搜索与状态流转可行性

该部分可行性高。理由如下：

1. 首版可由 SQL LIKE + 标签查询满足主要场景。
2. 状态机规则明确（在库、取出、迁移），实现边界清晰。
3. 可先保证“查得到、定位准”，再迭代检索质量。

### 6.3 扩展模块可行性

1. 过期提醒：规则驱动即可实现，技术风险低。
2. Agent 推荐：可先用规则模板，不必首版引入复杂模型。
3. 图像识别：可作为可选增强，避免影响主线交付。

## 七、风险评估

### 7.1 技术风险

1. 标注坐标在不同分辨率下偏移。

- 缓解：保存归一化坐标，前端渲染时按容器比例换算。

2. 搜索命中率不足。

- 缓解：建立标签词典、同义词映射和热词纠错。

3. 敏感信息泄露风险。

- 缓解：重要物品位置脱敏展示，关键页面二次验证。

### 7.2 工程风险

1. 范围膨胀导致延期。

- 缓解：严格执行 MVP，扩展功能放第二阶段。

2. 多人并行开发冲突。

- 缓解：先冻结接口，再并行开发；每日集成。

3. 文档缺失导致返工。

- 缓解：每个模块必须有接口文档与测试记录。

### 7.3 合规与伦理风险

1. 若接入第三方识别/大模型 API，需注意隐私与数据传输。
2. 课程项目定位应明确为学习与研究，不承诺商业级 SLA。

5. 状态机与审计日志

6. 团队协作规范

- Git 分支策略、PR 评审、接口先行与联调节奏。

## 十、建议实现边界与项目结论

### 10.1 第一阶段必须实现（MVP）

1. 空间图片管理与标注绑定。
2. 物品管理与状态流转。
3. 全局/局部搜索与位置反查。
4. 基础权限与重要物品保护。

### 10.2 第二阶段可选增强

1. 过期提醒可视化与批处理。
2. 同义词词典与检索优化。
3. Agent 场景化推荐与图像辅助录入。

### 10.3 暂不建议首版实现

1. 全自动识别全部物品。
2. 高复杂多模态大模型深度集成。
3. 多租户和分布式部署。

### 10.4 项目结论

Life-Inventory 选题具有明确用户痛点、清晰工程边界和较强展示价值。该项目兼具“可视化交互亮点”与“软件工程完整性”，适合作为软工作业。通过“空间映射 + 生命周期管理 + 搜索反查 + 分阶段扩展”路径，可在课程周期内实现可交付、可演示、可答辩的高质量成果。
